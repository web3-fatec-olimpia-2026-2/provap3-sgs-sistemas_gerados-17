O QUE MVC, MVT E MVP JÁ NOS DISSERAM
Separe o dado, a regra e a apresentação. E a regra de negócio não deve saber o que
é web.
Na Aula 07 extraímos um Service: a regra ganhou vida própria, testável sem HTTP.
Faltou um detalhe teimoso: mesmo com o Service, ainda sobra lógica na tela.
Não a regra de negócio — mas a lógica de como mostrar: o texto do status, o rótulo do
botão, o "LOTADO".
É dessa última sobra que o MVVM cuida. Ele é a quarta arquitetura — e é a que a segunda-feira de
vocês acabou de tocar com o Alpine.

===== Página 6 =====
A ideia do MVVM
Uma camada que prepara a vitrine
VIEWMODEL
Uma camada que pega o dado cru e devolve o dado já pronto para a tela — o texto do
status, o rótulo do botão, o preço formatado — sem saber que é uma tela. A View então
só exibe o que o ViewModel preparou.
Model
o dado cru: {numero, diaria, ocupado}
View
só desenha. Burra de propósito.
ViewModel
traduz dado cru em dado-pronto: status_label ,
botao_label , preco_formatado , disponivel .
PARA FIXAR O copeiro monta a bandeja; o garçom só serve. O garçom não cozinha.

===== Página 8 =====
A analogia que amarra tudo
A brigada do Resort, agora completa
Model — o estoque: a ficha crua do quarto, do jeito que está no sistema.
Regra/Service — a governança: decide tarifa, se pode reservar.
ViewModel — o maître: pega o prato pronto e emprata — decide o que o hóspede vê,
como o nome aparece no cardápio.
View — o garçom: leva à mesa. Não cozinha, não emprata. Só serve.
POR QUE SEPARAR O MAÎTRE DO GARÇOM
Se o garçom empratar no caminho, cada garçom emprata de um jeito. Centralize no
maître: um lugar só decide a aparência — e dá para conferir o emprato sem precisar
servir a mesa.

===== Página 9 =====
As quatro arquiteturas, lado a lado
Quatro nomes, um princípio
dado regra quem prepara a tela apresentação
MVC Model Controller — View
MVT (Django) Model View — Template
MVP Model Presenter Presenter View (passiva)
MVVM Model (Service) ViewModel View
O QUE O MVVM ACRESCENTA
Uma camada dedicada a preparar o que a tela mostra — o ViewModel. MVP tem algo
parecido (o Presenter empurra para a View); MVVM inverte: a View puxa do ViewModel.
Não decorem as siglas. A pergunta é sempre a mesma: onde mora a decisão de como
mostrar?

===== Página 10 =====
A ponte com a segunda-feira
Alpine.js é MVVM rodando no navegador
O QUE O X-MODEL FAZ
Na segunda, vocês ligaram um campo da tela a um dado com x-model . Mudou o dado,
mudou a tela; mudou a tela, mudou o dado. Isso é data binding — o coração do MVVM
clássico.
No navegador (Alpine), o ViewModel é reativo: o binding atualiza a tela sozinho.
No servidor (Python/Django), não há binding automático — o ViewModel vira uma
camada de preparação que você chama antes de renderizar.
PARA FIXAR Mesmo padrão, dois endereços: reativo no front (Alpine), de preparação no back (Python).

===== Página 11 =====
Delimitação em Python
Onde o MVVM encolhe — e onde não cabe
NO SERVIDOR, MVVM ENCOLHE
Sem binding, o ViewModel é só uma função ou uma classe que monta um dicionário
pronto para o template. Não invente "observables" no Django — isso é cerimônia que o
servidor não pede. (GIRIDHAR)
QUANDO NÃO CRIAR UM VIEWMODEL
Se a tela só mostra o dado como ele é — {nome} , {preço} — não há o que preparar.
ViewModel só se justifica quando há decisão de exibição: rótulo condicional,
formatação, estado derivado.
Antifachada de novo: a competência não é escrever o ViewModel. É decidir se há exibição a
preparar.

===== Página 15 =====
A ideia do Adapter
O adaptador de tomada
ADAPTER
Uma peça que veste um objeto com a interface que o cliente já espera, traduzindo as
chamadas por dentro. O cliente não muda; o objeto adaptado não muda; o adaptador
fica no meio.
O hóspede estrangeiro chega com plugue europeu — o ClienteNeon .
A parede do Resort tem tomada brasileira — a interface salvar/buscar .
O adaptador encaixa os dois. Ninguém troca o aparelho; ninguém quebra a parede.
PARA FIXAR Adapter não conserta a peça. Ele faz a peça caber.

Por que isso vale a pena
A prova é a substituibilidade
O TESTE QUE FECHA A QUESTÃO
O mesmo teste roda contra o armazenamento antigo e contra o Neon adaptado. Para o
serviço, viraram o mesmo tipo de coisa: um ReservaRepository .
Trocar de banco = trocar qual objeto você injeta. Uma linha.
A regra de negócio volta a conhecer uma interface. Nunca mais o if .

===== Página 18 =====
Delimitação em Python
Quando o Adapter é cerimônia inútil
DUCK TYPING DISPENSA O ADAPTER FORMAL
Se você controla as duas pontas e as interfaces já são parecidas, o Python aceita
qualquer objeto com os métodos certos — não precisa de classe Adapter. (GIRIDHAR)
QUANDO ELE SE JUSTIFICA
Quando o objeto adaptado é código de terceiro cuja assinatura você não pode mudar
— um driver de banco, uma biblioteca de pagamento, uma API externa. É exatamente o
caso do Neon.
Não envelope o que você mesmo escreveu só para "ficar bonito". Adapte o que você não
controla.

===== Página 21 =====
Agora no projeto de vocês
Identificar e decidir — não implementar à força
1. MVVM: achem na tela do projeto uma decisão de exibição (rótulo, formatação, estado
derivado). Vale extrair um ViewModel? Ou é exibição trivial?
2. Adapter: vocês migraram para o Neon na segunda. Há um ponto onde o código
conhece o banco direto? Um Adapter cabe ali — ou duck typing já resolve?
3. Em ambos: a resposta pode ser "não cabe". Isso também é decisão de design.
4. Registrem a decisão no Caderno de Design (ADR). Isso alimenta o Marco 2.
A TAREFA DE CASA É DECIDIR, NÃO APLICAR
Aplicar ou não aplicar — com a justificativa. Um "não aplicamos porque..." bem
argumentado vale tanto quanto um "aplicamos porque...".
