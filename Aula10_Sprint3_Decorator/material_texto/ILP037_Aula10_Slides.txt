===== Página 10 =====
A ideia do Decorator
Embrulhar para acrescentar
DECORATOR
Cada extra vira um embrulho que recebe uma reserva (ou outro extra já embrulhado),
implementa a mesma interface (preco /descricao ) e acrescenta a sua parte. Você
empilha os embrulhos em qualquer ordem, em tempo de execução.
A reserva é o presente; cada serviço extra é mais uma camada de papel em volta.
Quem abre vê a camada de fora, que por dentro chama a próxima, até a reserva-base.
Somar um extra = mais uma camada. Nada do que está dentro precisa mudar.
PARA FIXAR O embrulho não troca o presente — ele acrescenta por cima.

===== Página 12 =====
O trio estrutural, lado a lado
Adapter, Facade, Decorator
Padrão O que faz Intenção
Adapter traduz a interface de uma peça fazer caber
Facade cria interface nova para vários subsistemas esconder a complexidade
Decorator embrulha um objeto e soma responsabilidade acrescentar sem alterar
A DIFERENÇA PARA O ADAPTER
Os dois embrulham um objeto. Mas o Adapter muda a interface (para outra); o Decorator
mantém a mesma interface e só soma comportamento — por isso dá para empilhar.

===== Página 13 =====
Delimitação em Python
Onde o Decorator encolhe — e o @ que confunde
O @decorator DO PYTHON É OUTRA COISA
O @ do Python decora funções (embrulha um callable). O padrão Decorator do GoF
decora objetos para somar responsabilidade. Mesma ideia de "embrulhar", mecanismos
diferentes. (GIRIDHAR)
QUANDO NÃO USAR
Se os extras só somam um número fixo, uma lista de extras + soma já resolve — não
precisa de decorador. Ele ganha quando cada extra também muda comportamento. E
cadeias muito profundas ficam difíceis de depurar.
Antifachada de novo: a competência não é escrever o Decorator. É decidir se há
responsabilidade a somar.
